---
title: A forwarded Cliq message reaches the webhook with no readable text
category: Zoho Cliq specifics
apis: [/cliq/webhook, /api/v2/chats/{chatId}/messages, ZohoCliq.Messages.READ]
source: issue #223
---
- **A forwarded Cliq message reaches the webhook with no readable text, and the parser used to drop it silently.** The bot Message handler delivers `message` as a plain string (learning 103), and a forward's original author, timestamp and body are **not** part of that string. A forward with no caption therefore reached `parseCliqWebhookPayload` with an empty body, hit the `!bodyText` reject, and the webhook answered `400 invalid payload` **without logging anything** — so a dropped forward looked exactly like "Zoho never called us". Live proof (2026-09-05, bot `livia`): a forward plus a later `hallo?` produced exactly one dispatch, and only `hallo?` reached the transcript; the forwarded body appears nowhere under the state dir. The parser now recognises `forwarded_message` / `forwardedMessage` / `forwarded` / `forward` / `forwarded_content` / `original_message` / `originalMessage` (payload root **and** under `message`, plus the `params` wrapper), promotes the original text to the turn body when there is no caption, and renders an `⤷ Forwarded message from <author>` attribution block that is deliberately distinct from the `↩ Replying to` quote block. A recognised-but-unreadable forward (`is_forwarded: true` with nothing usable) still dispatches as `<forwarded message>` rather than dying. **Do not add a forward symbol to the Deluge handler script without first verifying the real Message-handler parameter set** — the Mention handler exposes a different set and an unavailable symbol fails permanently with `execution_handler_update_failed` (non-retryable, `src/bot-provisioning.ts`). Whatever Zoho does forward, the parser now keeps; what it does not forward stays recoverable through `GET /api/v2/chats/{chatId}/messages`, the same user-context read the attachment and quote paths already use.
