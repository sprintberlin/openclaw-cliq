A Node `fetch` transport failure typically surfaces as `TypeError: fetch failed`, with the real reason (`ECONNRESET`, `ETIMEDOUT`, `UND_ERR_SOCKET`, …) on `error.cause` — sometimes one level deeper under `errors[]` — so `String(err)` on a delivery path renders none of it. The cause is not guaranteed: a failure can carry no recognized code (or none at all), leaving the log line without one, so a missing `code=` is expected, not a bug. A transport failure after a POST is ambiguous — the request may already have been delivered — so the first ambiguous failure on a non-idempotent send lowers that send's attempt ceiling to `MAX_NON_IDEMPOTENT_NETWORK_ATTEMPTS = 2` total attempts. An ambiguous failure on attempt 1 therefore allows exactly one more attempt, and one on attempt 2 is the last. The cap is a ceiling, not a lifetime bound: when the first ambiguous failure arrives only after two or more other attempts (for example HTTP 5xx under a larger configured budget), the send has already made more than two attempts in total, so a mixed sequence must not be described as "at most two attempts overall". A failure that provably never reached the socket (`ECONNREFUSED`, `ENETUNREACH`/`EHOSTUNREACH`, connect-phase `ETIMEDOUT`/`UND_ERR_CONNECT_TIMEOUT`, `EAI_AGAIN`) keeps the full budget and is duplicate-safe; an HTTP-only 5xx sequence also keeps the full budget but is NOT duplicate-safe (an upstream proxy can accept the POST before failing), and the edit/token paths are idempotent. The retry-attempt log denominator must be the attainable physical ceiling, never a cap that shrinks below the attempt already taken.
